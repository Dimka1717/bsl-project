# Аудит модулей EME (первичный, по исходникам)

## Что проверено
- Ключевой модуль движка обмена с транзитной SQL: `eme/EmeWmsERPEngine/Ext/Module.bsl`.
- Вспомогательные утилиты настроек EME: `eme/EmeWmsУтилиты/Ext/Module.bsl`.

## Общая оценка корректности
- Архитектурно обмен реализован последовательно: есть `Begin.../Commit.../Rollback...`, разметка структуры сообщения, загрузка/выгрузка дочерних таблиц, обновление статусов, проверки целостности (например сверка `created_at` после обработки).
- Есть частичная защита строковых значений через `AsSqlValue()` (экранирование `'` в строках).
- Есть попытки защиты для некоторых ID (`StrReplace(HeaderId, "'", "''")`).

## Критические уязвимости

### 1) SQL-инъекции из-за конкатенации SQL (критично)
В модуле массово формируются SQL-строки через `+` и затем выполняются напрямую через `Connection.Execute(...)`/`Recordset.Open(...)`.

Особенно опасные места:
- удаление сообщений по `TableRow.id` без экранирования в `DeleteOldMessages()`;
- выборки по `ERPData.header.id` в `NextHeaderLine()` и `UpdateMessage()`;
- формирование фильтра по `State` в `GetHeaders()` без экранирования;
- универсальный `SelectLines()` выполняет произвольный `QueryText` как есть.

Риск: удаление/подмена данных в транзитной БД, обход бизнес-логики, потенциальный доступ к соседним таблицам при небезопасной СУБД/драйвере.

### 2) Не защищены SQL-идентификаторы (имена таблиц) из XML-конфига (критично)
Имена таблиц читаются из XML (`TableNode.Attributes...`) и потом напрямую подставляются в SQL (`""" + TableName + """`). При подмене файла настроек или его содержимого возможно выполнение SQL с произвольными идентификаторами.

Риск: чтение/модификация нецелевых таблиц, расширение поверхности атаки при компрометации настроек.

### 3) Неполная транзакционная безопасность в `Commit...` (высокий/критичный эксплуатационный риск)
`CommitExport()` и `CommitImport()` не обернуты в `Try/Except`. Если ошибка произойдет после `BeginTrans()`, но до `CommitTrans()`, есть риск «подвешенных» транзакций/блокировок, что может привести к DoS интеграции.

Риск: деградация/останов обмена, длительные блокировки таблиц, ручное восстановление.

## Замечания по hardening (не всегда критично, но важно)
- Дефолтный путь к конфигу (`C:\inetpub\...\ERPEngine.xml`) + загрузка conn string из XML увеличивает риск при слабом контроле файловой системы.
- Используется COM/ADODB напрямую; это усложняет безопасную параметризацию и контроль таймаутов/ошибок.

## Рекомендуемые меры (приоритет)
1. **Срочно перевести SQL на параметризованные команды** (ADODB.Command + Parameters), убрать конкатенацию значений.
2. **Ввести whitelist для имён таблиц/полей** из XML (регулярка + проверка на ожидаемый набор сообщений).
3. **Обернуть `CommitExport/CommitImport` в `Try/Except`** с гарантированным rollback в `Except`/`Finally`-паттерне.
4. Разделить доступы SQL-пользователя: только нужные таблицы/операции (минимальные привилегии).
5. Добавить аудит-лог попыток некорректных `id/state/table` и ограничение размеров входных параметров.
